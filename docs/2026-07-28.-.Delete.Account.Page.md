# Public account-deletion page at `/delete-account`

## Context

Google Play requires a publicly reachable URL where a user can request deletion of their account and data, listed in Play Console under Data safety. It has to work for someone who has already uninstalled the app, so it cannot sit behind a sign-in.

GeoNotes already has the whole server side: `requestAccountDeletion` marks the user row, revokes every session and drops every credential; the daily cron's `purgeExpiredDeletedAccounts` removes everything 30 days later; `DeleteAccountSection` exposes it in Settings. What is missing is a web page at a stable URL, and a way to authorize deletion without an existing session.

Outcome: `https://gnotes.vshub.app/delete-account` is a standalone public page that explains what deletion does, and lets anyone prove mailbox control with the normal 6-digit code and complete the deletion from the browser.

### Why an e-mail code is enough authorization

An e-mail code alone never creates a session in this app (`email-verify` mints only a 10-minute enroll token). But mailbox control is already sufficient to take an account over: the "Recover account" flow sends a code for any existing address and re-enrols a passkey onto that account, after which Settings can delete it. So authorizing deletion with an enroll token adds no attack surface, it just removes the pointless passkey ceremony in between. The deletion also stays reversible for 30 days by signing back in, which is the same undo the in-app path has.

### No account enumeration

The page requests the code in `mode: 'recover'`, which answers `{sent:true}` identically whether or not an account exists and only actually mails a code when one does. The new endpoint answers `{ok:true}` whether or not the address resolves to a user row.

## 1. Backend: `POST /api/auth/delete-account-by-email`

New file `worker/api/auth/delete-account-by-email.ts`, modelled on `worker/api/auth/email-change.ts` (the other enroll-token consumer) and on the existing `worker/api/auth/delete-account.ts`.

```
enforceAuthAbuseLimit(env, request)          // worker/_lib/rate-limit.ts
body.enrollToken must be a string            // else HttpError(400, 'bad body')
email = await verifyEnrollToken(env, token)  // worker/_lib/enroll.ts, throws 401
user  = SELECT id FROM users WHERE email = ? LIMIT 1
if (user) {
  await requestAccountDeletion(env, user.id, Date.now())   // worker/_lib/account-deletion.ts
  waitUntil(getEmailSender(env).sendAccountDeletionNotice(email).catch(() => {}))
}
return json({ ok: true })                    // constant response either way
```

No session is read and no `Set-Cookie` is emitted: this page is not signed in, and the caller's SPA session (if any, on the same browser) is already revoked server-side by `requestAccountDeletion`, so `requireUser` will answer `SESSION_REVOKED_REASON` on its next sync and the SPA wipes its local copy through the existing path in `src/lib/sync.ts`. The page must **not** call `wipeLocalAccountData()` itself, since the address deleted here need not be the account signed in on this browser.

Wire it in `worker/router.ts` alongside the existing `deleteAccount` import:

```ts
app.post('/api/auth/delete-account-by-email', deleteAccountByEmail)
```

## 2. Worker: serve the page at the clean URL

The plan was to map the clean URL in `worker/router.ts`, with a `servePage` helper in `worker/site.ts` rewriting the request path to `/delete-account.html` before handing it to `serveSite`. That loops: the assets binding's `html_handling` (default `auto-trailing-slash`) 307s `/delete-account.html` back to `/delete-account`, which the Worker rewrites again. `test/routing.integration.test.ts` caught it as "redirect count exceeded", which is precisely why that file exists.

The same setting is also the fix. `html_handling` resolves `/delete-account` to `delete-account.html` a step *before* `not_found_handling = "single-page-application"` can answer with the app shell, so the page needs no Worker route at all, and both `/delete-account/` and `/delete-account.html` redirect to the one clean URL for free. What the change ships instead is the setting spelled out explicitly in `wrangler.toml`, where it was previously implicit in the default, with a comment recording that a document now depends on it.

`run_worker_first = ["/*", "!/assets/*"]` already routes this path through the Worker, so the page still gets the non-production "GeoNotes Dev" `<title>` rewrite from `serveSite`'s catch-all. The CSP in `public/_headers` already allows `challenges.cloudflare.com` for scripts and frames and `connect-src 'self'` for the API, so it needs no change. No Android App Links intent filter exists in `android/app/src/main/AndroidManifest.xml`, so the URL always opens in a browser and never gets swallowed by the installed app.

## 3. Frontend: a second document, not a new SPA route

`src/lib/navigation.ts` is deliberately not a router ("the app lives at a single URL"). Keep that true by adding a second Vite entry.

- **`delete-account.html`** at the repo root, mirroring `index.html`: same `<meta viewport>`, `theme-color`, icons and `<script src="/theme-init.js">` for pre-paint theming; `<title>Delete your GeoNotes account</title>`; `<script type="module" src="/src/delete-account.tsx">`.
- **`vite.config.ts`**: add `build.rollupOptions.input = { main: 'index.html', deleteAccount: 'delete-account.html' }`. React, Tailwind and the shared components land in common chunks.
- **`vite.config.ts` PWA gotcha**: `VitePWA` generates a navigation fallback to `index.html`, which would hijack the clean `/delete-account` URL for anyone with the service worker installed. Add `/^\/delete-account/` to the existing `workbox.navigateFallbackDenylist` array next to the `/^\/api\//` entry.
- **`src/delete-account.tsx`**: `createRoot` with `<StrictMode><ThemeProvider><I18nProvider><DeleteAccountPage/></I18nProvider></ThemeProvider></StrictMode>`, plus `import './styles/global.css'` and the font. Deliberately no `registerSW`, no `initSync`, no `UnitsProvider`: this page owns no notes and no sync.
- **`src/screens/DeleteAccountPage.tsx`**: the page itself, a four-step flow modelled on `src/screens/AuthScreen.tsx` (which already does the same e-mail/code dance).

  1. `intro` - always rendered above the form, readable with no input: what deletion removes (account, every note, every passkey, every signed-in device), the 30-day grace window, that signing back in before it elapses cancels the deletion, and that the in-app path is Settings > Delete account. This block is the part Play actually reviews.
  2. `email` - `Input` + `TurnstileWidget` (`src/components/TurnstileWidget.tsx`, with `TURNSTILE_REQUIRED` gating the submit button exactly as `AuthScreen` does) -> `requestEmailCode(email, 'recover', turnstileToken)` from `src/lib/email-code.ts`.
  3. `code` - 6-digit `Input`, resend gated by `useCooldown` (`src/hooks/useCooldown.ts`) -> `confirmEmailCode(email, code)` -> `deleteAccountByEmail(enrollToken)`. Copy must be the recover-mode wording ("if an account exists for that address you will receive a code"), so a non-existent address is indistinguishable.
  4. `done` - confirms the account is scheduled for deletion in 30 days and that signing in before then cancels it.

  Errors go through the existing `authErrorKey` in `src/lib/auth-error.ts`. Wrap the destructive submit in the existing `ConfirmDialog` (`src/components/ConfirmDialog.tsx`) for parity with `DeleteAccountSection`.
- **`src/lib/email-code.ts`** (new): `requestEmailCode` and `confirmEmailCode` moved out of `src/lib/auth.ts`, plus `deleteAccountByEmail(enrollToken: string): Promise<void>` calling `apiFetch('/api/auth/delete-account-by-email', { enrollToken })`. Unlike `deleteAccount()` it does not wipe local data, for the reason in section 1.

  The move is what keeps the page small: importing the code flows from `auth.ts` would drag Dexie and the sync engine into a document that owns no notes. It went here rather than into `src/lib/account.ts` because that file is account management for an already signed-in user, which this is by definition not. Verified on the built output: `deleteAccount-*.js` is 4.2 kB and the shared chunk it pulls has no Dexie in it.
- **i18n**: new `deleteAccount.*` keys added to all three of `src/locales/{en,es,pt}.json`. The dictionaries are flat and untyped, so a missing key silently falls back; add every key to all three files in the same pass.

## 4. Tests

- `test/account-deletion.integration.test.ts` - a `describe` for the by-email endpoint against the real migrations via `createTestDb()`: a valid enroll token stamps `deletion_requested_at`, revokes sessions and drops credentials; a tampered or expired token gives 401 and changes nothing; an address with no account gives 200 and changes nothing. Posts through the router with `Origin: TEST_ORIGIN` as `test/play-review-access.integration.test.ts` does. This belongs here per AGENTS.md ("anything whose correctness lives in SQL").

  The plan also called for a `worker/router.test.ts` case proving the POST route is wired. It cannot live there: `verifyEnrollToken` needs workerd's `crypto.subtle.timingSafeEqual`, and the polyfill for it is in `test/support/`, which `tsconfig.worker.json` deliberately excludes. The integration tests above drive the same route through `app.request` against real SQLite, which is strictly stronger, so the case was dropped rather than relocated.
- `test/routing.integration.test.ts` - `GET /delete-account` returns 200 `text/html` whose body is the delete page, not the SPA shell, plus the same from `/delete-account/` and `/delete-account.html`, plus a counter-check that every other path still gets the shell. Asserted on which entry chunk the document loads (`deleteAccount` vs `main`), not on the `<title>`: `serveSite` rewrites the title of *every* document to "GeoNotes Dev" off production, which would make the two indistinguishable.

## 5. Verification

```
pnpm typecheck && pnpm lint
pnpm build                 # must precede the integration project
pnpm test
pnpm preview               # serves dist/ on :8788, staging tunnel in front
```

Then, by hand (browser checks are the user's, per AGENTS.md):

1. Open the staging `/delete-account` signed out, in a private window. The intro copy renders with no session, in the browser's language.
2. Run the flow against a throwaway account: e-mail -> Turnstile -> code (dev echoes it) -> confirm. Expect the deletion notice e-mail and the `done` step.
3. Check D1: `deletion_requested_at` set, `sessions.revoked_at` stamped, `credentials` rows gone for that user.
4. Sign back in with "Recover account" and confirm the deletion is cancelled (`createSession` clears the mark) and the notes come back.
5. Enter an address with no account: identical UI up to the code step, no code arrives, no error that reveals anything.
6. Load the SPA at `/`, then reload `/delete-account` with the service worker active, to confirm the `navigateFallbackDenylist` entry keeps the SW from serving the app shell there.

Passkeys and e-mail sign-in only work on `https://gnotes.vshub.app`, so run steps 2-4 against the staging tunnel or production, not `workers.dev`.
